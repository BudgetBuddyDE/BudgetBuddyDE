# `@budgetbuddyde/db`

## About

A shared database schema library for BudgetBuddy services. This package provides Drizzle ORM schemas, types, and utilities for both the backend and authentication services, ensuring a consistent database structure across all services.

## Features

- **Drizzle ORM Integration**: Modern TypeScript ORM with type-safe queries
- **Multi-Schema Support**: Separate schemas for backend (`budgetbuddy_backend`) and auth (`budgetbuddy_auth`)
- **Type Safety**: Fully typed database entities with Zod validation schemas
- **Schema Generation**: Automated schema generation for Better-Auth integration
- **Migration Support**: Built-in migration tools via Drizzle Kit
- **Shared Library**: Used across all BudgetBuddy services to avoid duplication

## Installation

This is an internal package used within the BudgetBuddy monorepo. It can be referenced in other packages via workspace dependencies:

```json
{
  "dependencies": {
    "@budgetbuddyde/db": "workspace:*"
  }
}
```

## Getting Started

### Basic Usage

```typescript
import {backendSchema, categories, transactions} from '@budgetbuddyde/db/backend';
import {authSchema, user, session} from '@budgetbuddyde/db/auth';
import {drizzle} from 'drizzle-orm/node-postgres';

// Initialize database connection
const db = drizzle(process.env.DATABASE_URL);

// Query backend data
const userCategories = await db.select().from(categories).where(eq(categories.ownerId, userId));

// Query auth data
const userSession = await db.select().from(session).where(eq(session.userId, userId));
```

## Database Schemas

### Backend Schema (`budgetbuddy_backend`)

The backend schema contains all business logic tables:

#### Categories

Manage transaction categories for income and expenses.

```typescript
{
  id: uuid(PK);
  ownerId: varchar;
  name: varchar(40);
  description: text;
  createdAt: timestamp;
  updatedAt: timestamp;
}
```

#### Payment Methods

Store user payment methods (bank accounts, credit cards, etc.).

```typescript
{
  id: uuid(PK);
  ownerId: varchar;
  name: varchar(40);
  provider: varchar(32);
  address: varchar(32);
  description: text;
  createdAt: timestamp;
  updatedAt: timestamp;
}
```

#### Transactions

Record individual financial transactions.

```typescript
{
  id: uuid (PK)
  ownerId: varchar
  categoryId: uuid (FK -> categories)
  paymentMethodId: uuid (FK -> paymentMethods)
  processedAt: timestamp
  receiver: varchar(100)
  transferAmount: double
  information: text
  createdAt: timestamp
  updatedAt: timestamp
}
```

#### Recurring Payments

Manage scheduled recurring payments. `startsOn` is the first execution and anchors later occurrences. Month-based plans retain the anchor day and clamp to the last day of shorter months. Paused records remain stored but are not processed.

```typescript
{
  id: uuid (PK)
  ownerId: varchar
  categoryId: uuid (FK -> categories)
  paymentMethodId: uuid (FK -> paymentMethods)
  executionPlan: enum ('daily' | 'weekly' | 'biweekly' | 'monthly' | 'quarterly' | 'yearly')
  startsOn: date (YYYY-MM-DD)
  paused: boolean
  receiver: varchar(100)
  transferAmount: double
  information: text
  createdAt: timestamp
  updatedAt: timestamp
}
```

#### Budgets

Define income and expense budgets.

```typescript
{
  id: uuid (PK)
  ownerId: varchar
  type: enum ('i' | 'e') // income or expense
  name: varchar(32)
  budget: double
  description: text
  createdAt: timestamp
  updatedAt: timestamp
}
```

### Auth Schema (`budgetbuddy_auth`)

> [!TIP]
> For more information about the schema generation and migration have a look into [the documentation](https://www.better-auth.com/docs/basic-usage#migrate-database).

The auth schema is generated by Better-Auth and contains authentication-related tables:

#### User

Store user account information.

```typescript
{
  id: text(PK);
  name: text;
  email: text(unique);
  emailVerified: boolean;
  image: text;
  createdAt: timestamp;
  updatedAt: timestamp;
}
```

#### Session

Manage user sessions.

```typescript
{
  id: text (PK)
  expiresAt: timestamp
  token: text (unique)
  userId: text (FK -> user)
  ipAddress: text
  userAgent: text
  createdAt: timestamp
  updatedAt: timestamp
}
```

#### Account

OAuth provider accounts linked to users.

```typescript
{
  id: text (PK)
  accountId: text
  providerId: text
  userId: text (FK -> user)
  accessToken: text
  refreshToken: text
  idToken: text
  accessTokenExpiresAt: timestamp
  refreshTokenExpiresAt: timestamp
  scope: text
  password: text
  createdAt: timestamp
  updatedAt: timestamp
}
```

## Migration Workflows

### Prerequisites

> [!WARNING]
> Make sure that the `DATABASE_URL` environment variable is set and points to the target database where the schema should be applied. If the environment variable is not set, the migration process will fail with an error.

```bash
export DATABASE_URL="postgresql://user:password@localhost:5432/budgetbuddy"
```

### Generating Schemas

The database schema is defined using Drizzle ORM. To modify the schema:

1. Edit the table definitions in `src/backend/tables.ts` or `src/auth/tables.ts`
2. Update relationships in `src/backend/relations.ts` if needed
3. Generate migration files

### Auth Schema Generation

The database schema required for the integrated Better Auth backend can be generated using the @better-auth/cli:

```bash
vp run ba:schema-generate
```

> [!WARNING]
> Nach dem Erstellen/Anpassen des Datenbankschemas für den integrierte Authentifizierung im Backend können manuelle Änderungen notwendig sein, um nahtlose Integration mit dem Backend-Schema zu gewährleisten. Es ist wichtig, die generierten Schemas sorgfältig zu überprüfen und sicherzustellen, dass sie mit den Anforderungen des Backend-Schemas kompatibel sind.

### Creating Migrations

Generate migration SQL files from your schema definitions:

```bash
vp run db:generate
```

This command will:

1. Run `ba:schema-generate` to generate auth schemas
2. Format the generated schema files with Prettier
3. Generate migration SQL files using Drizzle Kit

The migration files will be created in the `drizzle/` directory of the services that use this package.

### Applying Migrations

Apply the generated migrations to your database:

```bash
vp run db:migrate
```

This will execute all pending migrations in the correct order.

### Category hierarchy upgrade: owner integrity preflight

Before upgrading to the category hierarchy release, put the backend (including recurring jobs, imports, and other
database writers) into maintenance mode. Take a restorable PostgreSQL backup and rehearse the upgrade on a restored
copy. Keep writers stopped until all migrations, including `0017_category_owner_guard`, have succeeded on the target.

From the repository root, run the read-only report as an operator with access to all owners:

```bash
psql -X "$DATABASE_URL" -f packages/db/scripts/preflight-owner-integrity.sql
```

**Require zero result rows**, not just exit code zero. The report includes transaction and recurring category and
payment-method assignments, plus budget/category links. It exposes internal record and owner IDs; store its output
privately. Run it before `0015` on pre-feature databases: `0015` itself validates its foreign keys, so it can stop the
upgrade before `0017` runs. On databases already at `0015` or `0016`, `0017` checks existing assignments and verifies
the category and budget-link foreign keys are validated. The report works before `0015`; `0017` additionally checks
the stored link owner against both referenced rows. Neither guard reconciles data automatically.

If conflicts exist, leave the app stopped and review each record with the responsible data owner. A reference with no
reported owner is missing. Identify or create the correct category or payment method owned by the record's owner;
do not infer a replacement from a shared name or change a financial record's owner. For each approved correction,
use an explicit SQL transaction that qualifies the update by record ID, recorded owner, and original reference ID.
Verify the replacement belongs to that owner and exactly one intended record was updated before committing. For a
budget link, replace only the approved association, retaining the budget and avoiding a duplicate link. Record the old
and new IDs in the change record, and leave ambiguous records untouched until resolved. For a missing budget, verify
the original association from backup and have the owner approve an explicit link correction before proceeding.
Do not delete financial records,
disable constraints, or mark migrations applied to get past an error.

Run the report again, require zero rows, then run `pnpm --filter @budgetbuddyde/db run db:migrate`. If migration fails,
keep writers stopped and investigate rather than starting the new backend.

After reconciliation and successful migrations, and **before smoke checks or reopening traffic**, rotate the API
response cache to an unused, dedicated Redis logical database or instance (`REDIS_URL` / `REDIS_DB`), or purge only
API response-cache keys in the configured response-cache database. Keep old backend instances stopped so they cannot
repopulate stale data. For a targeted purge, use `SCAN` with `MATCH 'cache:*'`, then `UNLINK` only confirmed response
payload and `cache:generation:*` keys owned by this deployment. If that namespace is shared with other applications,
use a dedicated response-cache database instead. Never use `FLUSHDB` or `FLUSHALL`, and never flush or repoint
auth/session Redis (`AUTH_REDIS_URL` / `AUTH_REDIS_DB`).

With public traffic still blocked, smoke-test owner-scoped category, transaction, recurring-payment, and budget reads.
On cache-enabled routes, verify the first read is a cache miss and matches the reconciled data. Reopen traffic only
after the checks pass.

## Usage in Services

### Backend Service

```typescript
import {drizzle} from 'drizzle-orm/node-postgres';
import {categories, transactions} from '@budgetbuddyde/db/backend';
import {eq} from 'drizzle-orm';

const db = drizzle(process.env.DATABASE_URL);

// Fetch user categories
const userCategories = await db.select().from(categories).where(eq(categories.ownerId, userId));
```

### Auth Service

```typescript
import {drizzle} from 'drizzle-orm/node-postgres';
import {user, session} from '@budgetbuddyde/db/auth';
import {eq} from 'drizzle-orm';

const db = drizzle(process.env.DATABASE_URL);

// Fetch user by email
const foundUser = await db.select().from(user).where(eq(user.email, email)).limit(1);
```

## Important Notes

> [!IMPORTANT]
> This package is a shared library used across all BudgetBuddy services and the integrated backend authentication to ensure a consistent database schema and to avoid code duplication. The schema is defined using Drizzle ORM and can be generated and applied using the @better-auth/cli and Drizzle Kit.

> [!WARNING]
> When making schema changes, ensure that:
>
> 1. All dependent services are updated accordingly
> 2. Migrations are tested in a development environment first
> 3. The auth and backend schemas remain compatible
> 4. Foreign key relationships are maintained
